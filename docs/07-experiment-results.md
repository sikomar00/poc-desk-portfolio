# 실험 결과

## 요약
두 모델(`nvidia/nemotron-3-super-120b-a12b`, `openai/gpt-oss-20b`) 실험이 모두 끝났습니다. **사전 고정 규칙에 따른 종합 판정은 "불명"입니다.**

1. **KPI 사전은 정확도를 크게 올렸습니다.** 두 모델 모두 사전 없이는 거의 못 맞혔고(1%, 7%), 사전을 주자 66%, 59%가 되었습니다(+65%p, +52%p). 지지 기준(≥ 15%p)을 크게 넘었습니다.
2. **그러나 일관성이 기준에 못 미칩니다.** 같은 질문 5번의 결과가 같은 비율(B 일치율)이 71%, 74%로 기준(90%)에 미달했습니다. "정확도 차이 ≥ 15%p **이고** B 일치율 ≥ 90%"가 지지 조건이었으므로 두 모델 모두 불명이고 종합도 불명입니다. **기준은 결과를 본 뒤 바꾸지 않았습니다.**
3. **큰 모델이 작은 모델보다 낫다고 말할 수 없습니다.** B 정확도 66% 대 59%의 95% 구간(56~75%, 49~68%)이 겹칩니다.
4. **환불률은 두 모델 모두 사전을 줘도 거의 틀렸고(3/20, 3/20), 원인을 데이터로 확인했습니다.** 둘 다 "결제 완료"를 `status='PAID'`로 해석해 결제 후 취소된 주문을 빠뜨렸습니다. 사전에는 포함하라고 **명시되어 있었는데도** 따르지 않았습니다(5절 2번).
5. **H3(대사로 오류 검출)은 지지**입니다(틀린 SQL 10/10, 실제 LLM 매출 오답 14/14, 정답 거짓 경보 0). 다만 이것은 구조상 필연이고, 의미 있는 발견은 **허용 오차를 0.1%만 둬도 실제 오답 3개를 놓친다**는 것과 **가장 많이 틀린 환불률에는 대사할 정답 출처가 없다**는 것입니다(6절).
6. **정답 출처가 없는 지표(환불률 등)의 검증 방법 세 가지를 소급 시험**했습니다(7절). 100% 검출처럼 보이는 조합은 정답의 82%에 경보를 울려 쓸 수 없었고, 쓸 만한 것은 교차 모델 불일치와 반복 4/5 미만 일치로 정밀도 58~63%(기준선의 1.7~1.8배)였습니다. **검증기가 아니라 사람에게 보낼 후보를 추리는 선별기**입니다. 오류가 두 모델에서 같으면 교차 확인도 소용없습니다.

> 📘 **개념 학습 — "사전을 주면 된다"는 절반만 맞다**
> 사전은 모델이 추측할 수 없는 규칙을 알려 주는 데는 효과가 컸습니다. 하지만 **규칙이 글로 적혀 있어도 모델이 그것을 매번 따르지는 않습니다.** 그래서 현업의 BI 시스템은 정의를 글이 아니라 실행 가능한 형태(지표 계산식, 컬럼 매핑, 검증 쿼리)로 두고, 결과를 별도 출처와 대사합니다. 이 프로젝트의 realDefinition 설계(정의 확정 → SQL 생성 → 원장 대사)가 바로 그 구조입니다.

## 5. 사후 분석 (탐색적 — 사전 고정 기준과 구별)

아래는 결과를 본 뒤 원인을 찾은 **탐색적 분석**이며 가설 검증의 증거로 쓰지 않습니다. 재현: `python experiment/analyze_run.py <기록 파일>`

1. **취소율은 사전이 대부분 고쳤습니다**(A 0/20, 0/20 → B 19/20, 15/20). "결제 전·후 취소를 모두 센다, PENDING 제외, 주문일 기준"처럼 **모델이 추측할 수 없는 규칙**이 사전에 있었기 때문으로 보입니다.
2. **환불률은 두 모델 모두 사전을 줘도 3/20이었고, 원인은 `status='PAID'` 필터입니다(확인함).**
   - 1월 환불률의 골드는 6.80%인데, 두 모델이 낸 틀린 값은 2.16%였습니다. `status='PAID'` 주문만으로 분자·분모를 계산하면 정확히 2.16%가 나옵니다(DB에서 재계산해 일치 확인). 결제 후 취소된 주문의 전액 환불과 그 상품금액을 빠뜨린 결과입니다.
   - **정정:** 이 문서의 이전 판(gpt-oss 결과만 본 시점)은 이것을 "사전 문구의 모호함 때문일 가능성이 크다"고 해석했습니다. 확인해 보니 **사전에는 "취소된 주문도 포함한 결제 완료 주문 전체", "결제 후 취소의 전액환불 포함"이라고 명시**되어 있었습니다. 모호해서가 아니라 **명시된 규칙을 두 모델이 따르지 않은 것**입니다. 가능한 이유는 "결제 완료"를 상태값 `PAID`로 바로 연결하는 강한 습관이나 여러 조건이 겹친 정의를 단순화하는 경향 등이며, 어느 쪽인지는 아직 모릅니다.
   - 두 모델에서 같은 실패가 나왔으므로 모델 하나의 특이한 실수일 가능성은 낮습니다.
3. **Q19("2월 주문 몇 건이야?")는 모델마다 달랐습니다.** gpt-oss는 B에서도 0/5(사전의 별칭 "주문 수"를 무시하고 전체 주문을 센 150건, 골드 129건), nemotron은 3/5였습니다. 사전을 프롬프트에 넣는 것과 모델이 질문의 단어를 사전 항목에 연결해 쓰는 것은 별개의 문제입니다.
4. **사전이 필요 없는 질문도 모델에 따라 다릅니다.** Q18("결제 건수")은 gpt-oss가 사전 없이 5/5였지만 nemotron은 1/5였습니다. 일상적 의미와 정의가 같으면 사전이 필요 없다는 이전 판의 결론은 모델에 따라 달라지므로 일반화하지 않습니다.
5. **틀린 값이 정답 근처인 경우가 많습니다.** 매출의 B 오답은 골드의 0.98~1.0배, 객단가는 0.99배 안팎이었습니다. 사람이 보면 맞아 보이는 **거의 맞는 오답**이며, 이런 오류를 잡으려고 정확히 일치해야 통과시키는 대사(F6)가 필요합니다. 매출은 원장이 있으므로 같은 규칙으로 이 오답을 모두 걸러낼 수 있습니다(구조상 정확히 다르면 경고).
6. **정확도와 일치율은 다른 지표입니다.** A는 정확도 1~7%인데 일치율이 67~68%인 이유는 **같은 오답을 반복**하기 때문입니다. 일치율만 보면 속을 수 있다는 06 문서의 개념 박스가 실제 데이터로 확인되었습니다.
7. **큰 모델의 우위는 확인되지 않았습니다.** B 정확도 66% 대 59%는 구간이 겹칩니다. 응답은 nemotron이 더 빨랐습니다(35초 대 65초). "크기 ≠ 품질" 가능성도 열려 있습니다.

## 6. H3 결과: 대사는 틀린 매출 SQL을 걸러내는가? (LLM 없이 실행)

재현: `python experiment/h3_reconcile.py` (출력 기록: `experiment/h3_output.txt`)

**대사 규칙(F6 시제품):** SQL 결과와 원장의 차이가 허용 오차 이내면 PASS, 아니면 FLAG.

### 6-1. 사전 고정 기준 대비 판정
06 문서의 규칙은 "원장과 **완전히 일치하지 않으면** 경고"였습니다. 틀린 SQL 10개 중 **10개 모두 검출(100%)** 되어 지지 기준(≥ 80%)을 충족합니다. **판정: H3 지지.**

다만 이 100%는 **구조상 필연**입니다. 정답은 원장과 같은 값이므로, 원장과 다른 값은 정의상 틀린 값입니다. 이 결과가 증명하는 것은 "대사가 동작한다"는 것이지 "대사가 똑똑하다"는 것이 아닙니다. 아래의 허용 오차 민감도와 거짓 경보 확인이 더 의미 있는 부분입니다.

### 6-2. 거짓 경보 확인
| 대상 | 결과 |
|---|---|
| 공식(정답) SQL 3개월 | 3/3 PASS, 거짓 경보 0건 |
| 실제 LLM이 정답을 낸 매출 호출 36회 | 거짓 경보 0건 (모든 허용 오차에서) |

### 6-3. 허용 오차를 두면 어떻게 되나 (민감도)
"1% 정도는 봐주자"는 현실에서 흔한 생각이라 허용 오차를 바꿔 가며 놓치는 오류를 셌습니다.

| 허용 오차 | 틀린 SQL 10개 검출 | 실제 LLM 오답 14개 검출 | 정답 거짓 경보 |
|---|---:|---:|---:|
| **정확히 일치(0%)** | **10/10** | **14/14** | 0/36 |
| ±0.1% | 10/10 | 11/14 | 0/36 |
| ±0.5% | 10/10 | 11/14 | 0/36 |
| ±1% | 9/10 | 10/14 | 0/36 |
| ±2% | 7/10 | 6/14 | 0/36 |
| ±5% | 5/10 | 6/14 | 0/36 |

- **허용 오차를 0.1%만 둬도 실제 LLM 오답 3개를 놓칩니다.** 이 3개는 상대 오차가 0.00~0.02%인 오답으로, 사람이 보면 같은 숫자로 보이는 "거의 맞는 오답"입니다.
- 1%를 두면 가장 거의 맞는 오답(환불을 환불일 월에 귀속, −0.62%)이 빠져나갑니다. 5%를 두면 절반이 통과합니다.
- 반대로 허용 오차를 두어서 얻는 이득(거짓 경보 감소)은 이 데이터에서는 **0건**이었습니다. 정답은 어떤 허용 오차에서도 경보가 없었기 때문입니다. 정수 금액 계산에서는 정답이 원장과 정확히 같아서 허용 오차가 필요 없습니다.
- 결론: **매출처럼 정확한 정답 출처가 있는 지표는 허용 오차 0으로 대사한다**(D-024). 05 문서의 오답 V4(−0.62%)가 이 결론의 근거 사례입니다.

> 📘 **개념 정리 — 거짓 경보와 놓침은 맞바꿈 관계**
> 허용 오차를 키우면 정답에 경보가 울리는 일(거짓 경보)은 줄지만, 틀린 값을 통과시키는 일(놓침)이 늘어납니다. 어느 쪽이 더 비싼지는 상황이 정합니다. 금액 보고서에서는 틀린 값 통과가 훨씬 비싸므로 놓침을 0으로 만드는 쪽을 택했습니다. 반대로 정답이 원래 흔들리는 지표(추정치 등)라면 허용 오차가 필요합니다.

### 6-4. 대사의 한계 — 가장 많이 틀린 지표는 대사할 수 없다
- 이 대사는 **독립적인 정답 출처가 있는 지표**(여기서는 매출의 원장)에만 쓸 수 있습니다. 환불률·취소율·객단가·유효 주문 수에는 원장이 없습니다.
- 가장 많이 틀린 지표가 환불률(3/20, 3/20)인데, **바로 그 지표에는 대사 장치가 없습니다.** 2.16%처럼 그럴듯한 값은 사람도 의심하기 어렵습니다.
- 정답 출처가 없을 때 쓸 수 있는 후보: (a) 서로 다른 방법으로 한 번 더 계산해 비교, (b) 지표 간 관계 검사(예: 1분기 값은 월별 값으로 재구성되어야 함, 비율은 0~100% 범위), (c) 같은 질문 여러 번 실행해 결과가 갈리면 경보(일치율 활용). **이 세 방법은 아직 시험하지 않은 아이디어**이며 후속 과제입니다.

## 7. 정답 출처가 없는 지표의 검증 — 세 방법 소급 시험 (LLM 호출 없음)

6-4에서 "환불률처럼 대사할 정답이 없는 지표는 어떻게 검증하나"를 남겼습니다. 후보 세 방법을 **골드(정답)를 쓰지 않고** 기존 기록(조건 B, 두 모델)에 적용해 보고, 골드는 방법을 채점하는 데만 썼습니다. 재현: `python experiment/verify_without_gold.py` (출력: `experiment/verify_without_gold_output.txt`)

| 방법 | 규칙 |
|---|---|
| 1 이중 계산(교차 모델 일치) | 다른 모델도 같은 질문을 풀어 값이 다르면 경보 |
| 2 지표 간 관계 검사 | 같은 회차 답들끼리 지켜야 할 관계(1분기 매출 = 월별 합, 객단가 = 매출 ÷ 건수, 1분기 비율은 월별 비율 범위 안, 값의 범위)가 깨지면 경보 |
| 3 반복 실행 불일치 | 같은 질문 5회 결과가 5/5 일치하지 않으면 경보 (3'는 4/5 미만일 때 경보) |

값이 없는 호출 9회(SQL 오류 등)는 이미 실패가 드러났으므로 제외해 분석 191회(오답 66, 정답 125)를 대상으로 했습니다.

### 7-1. 결과 (조건 B = 실제 운영 조건)

| 방법 | 오답 검출 | 정답에 거짓 경보 | 경보의 정밀도 (경보 중 진짜 오답 비율) |
|---|---:|---:|---:|
| 1 교차 모델 불일치 | 52/66 (79%) | 31/125 (25%) | **63%** (1.8배) |
| 2 지표 간 관계 위반 | 37/66 (56%) | 58/125 (46%) | 39% (1.1배) |
| 3 반복 5/5 일치만 통과 | 61/66 (92%) | 75/125 (60%) | 45% (1.3배) |
| **3′ 반복 4/5 미만 일치** | 48/66 (73%) | 35/125 (28%) | **58%** (1.7배) |
| 1+2+3 중 하나라도 | 66/66 (100%) | 102/125 (82%) | 39% (1.1배) |
| (비교) 6절의 정확한 대사 | 14/14 | 0/36 | 100% |

"배"는 아무 답이나 골라 경보로 찍었을 때의 정밀도(오답 비율 35%) 대비 몇 배 나은지입니다.

### 7-2. 읽는 법과 발견

1. **100% 검출은 속임수에 가깝습니다.** 세 방법을 합치면 오답을 모두 잡지만 정답의 82%에도 경보가 울려서, 정밀도가 아무 답이나 찍는 것(35%)과 거의 같습니다(39%). 사용할 수 없는 경보입니다. **검출률만 보고 방법을 고르면 안 됩니다.**
2. **쓸 만한 후보는 방법 1과 3′입니다.** 정확한 대사만큼은 아니지만 정밀도 58~63%로 기준선의 1.7~1.8배입니다. 대신 정답의 25~28%에 경보가 울리고 오답의 21~27%는 놓칩니다. **검증기가 아니라 "사람이 볼 후보를 추려 주는 선별기"** 입니다. 방법 1은 191개 답 중 83개(43%)를 사람에게 보내서 오답 52개를 잡습니다.
3. **방법 1의 약점은 상관된 오류입니다.** 놓친 오답 14개는 **두 모델이 같은 틀린 값**을 낸 경우였습니다. 환불률의 2.16%처럼 두 모델이 같은 습관(`status='PAID'` 필터)으로 틀리면 서로 확인해도 소용없습니다. 모델을 늘리면 오류는 독립이 아니라서 효과가 제한적입니다.
4. **방법 2는 "어디가 틀렸는지"는 못 알려 주지만 "뭔가 틀렸다"는 신호는 정확합니다.** 관계 위반 30건은 **모두(100%)** 관련된 답 중 하나 이상이 실제 오답이었습니다. 다만 위반된 관계에 묶인 답을 전부 의심하게 되어 정답에도 경보가 퍼집니다(답 단위 정밀도 39%). 또 검출은 56%에 그쳐, 일관되게 틀리는 답들은 서로 관계가 맞아서 통과합니다.
5. **방법 3(반복)은 일관되게 틀린 오답을 못 잡습니다.** 조건 B에서는 답이 흔들려서 잘 걸렸지만, 사전 없이 같은 오답을 반복하는 조건 A에서는 세 방법을 합쳐도 오답 191개 중 26개가 모두 통과했습니다. 반복 불일치는 "흔들리는 오류"만 봅니다.
6. **참고: 다수결.** 질문마다 5회 중 가장 많은 값을 고르면 정답인 질문이 gpt-oss 13/20, nemotron 15/20이었습니다(호출 단위 정확도 59%, 66%보다 질문 단위 65%, 75%로 높음). 반복 실행은 검증뿐 아니라 보정에도 약간 도움이 됩니다.

> 📘 **개념 학습 — 정밀도는 기준선과 함께 봐야 한다**
> "경보 중 60%가 진짜 오답"이라는 숫자는 원래 오답이 얼마나 흔한지에 따라 좋을 수도 나쁠 수도 있습니다. 이 실험에서는 오답이 35%라서 아무 답이나 찍어도 35%가 맞습니다. 그래서 기준선 대비 몇 배인지를 같이 적었습니다. 또 **오답이 드물수록 같은 거짓 경보율에서도 정밀도가 크게 떨어집니다.** 예를 들어 방법 1의 검출 79%, 거짓 경보 25%를 오답 비율 5%인 시스템에 적용하면 경보 정밀도는 약 14%로 계산됩니다(계산값이며 측정한 것이 아님). 시스템이 좋아질수록 경보는 오히려 쓸모없어질 수 있습니다.

### 7-3. 이 시험의 한계
| 한계 | 영향 |
|---|---|
| 방법과 관계 규칙을 결과를 본 뒤에 고안했고 같은 데이터로 시험 | 낙관적일 수 있음. 일반화 증거가 아니라 **탐색적 소급 시험** |
| 모델 2개, 질문 20개 | 방법 1은 모델이 둘뿐이라 교차 확인의 폭이 좁음 |
| 방법 2의 관계는 이 20개 질문의 구조(월별, 분기)에 맞춰 만든 것 | 다른 질문 세트에는 다른 관계가 필요 |
| 오답 비율이 35%로 높은 환경 | 7-2의 개념 박스처럼 오답이 적은 환경에서는 정밀도가 달라짐 |

### 7-4. realDefinition 설계에 주는 것 (D-025)
- **정답 출처가 있는 지표**(매출): 허용 오차 0의 정확한 대사 → "검증됨" 표시 (6절).
- **정답 출처가 없는 지표**: 어떤 방법으로도 "검증됨"을 붙이지 않고, 방법 1(교차 모델)이나 3′(반복 4/5 미만 일치)로 **"사람이 확인할 것" 신호**만 줍니다. 신호가 없다고 맞다는 뜻이 아니라는 점을 화면에 적습니다.
- **더 근본적인 해법은 이번 시험의 범위 밖**입니다. LLM이 질문마다 SQL을 새로 짜게 하지 않고, **사람이 검토한 지표 계산식(정의별 검증된 SQL)을 직접 실행**하게 하는 방식(시맨틱 레이어)입니다. 환불률의 오답이 모델 습관에서 나온 체계적 오류였으므로, 오류를 사후에 걸러내는 것보다 **애초에 틀릴 수 없는 경로를 만드는 쪽**이 효과가 클 가능성이 있습니다. 이 가설은 아직 시험하지 않았습니다.
- 방법 1과 3′의 임계값은 이 소급 시험에서 고른 것이므로, 사전 v2 후속 실험에서 **미리 고정한 규칙으로 보류 질문에 적용해 다시 평가**합니다(그때는 사후 분석이 아닌 사전 지정 평가).

## 8. 해석 시 주의 (한계)

| 한계 | 영향 |
|---|---|
| 모델 2개, 온도 0.7 하나 | 다른 모델·온도에서는 다를 수 있음 |
| 질문 20개, 독립 질문은 19개에 가까움 | 같은 질문 5회는 독립이 아니라 신뢰구간이 실제보다 좁게 보임 |
| 사전과 질문을 같은 사람(나)이 작성 | 사전 문구가 내 정의에 맞춰져 있어 다른 사람이 썼다면 결과가 달랐을 수 있음 |
| 사후 분석은 탐색적 | 5절의 원인 해석 중 "이유"는 후속 실험이 필요(2번의 `status` 필터 사실 자체는 데이터로 확인) |
| 합성 데이터 3개월 | 현실 일반화 제한 |
| 정답(골드)은 내가 정한 정의 v1에 대한 정답 | 정의 자체의 타당성은 이 실험이 판단하지 않음 |

## 9. 후속 실험 계획 (탐색적, 별도 보고)

**설계와 사전 지정 판정 규칙은 [08 문서](08-experiment-v2-design.md)에 동결해 두었습니다(D-026).**

**원칙:** 이번 실험(사전 v1)의 결과는 **고치지 않고 그대로 둡니다**(D-023). 결과를 본 뒤 사전을 고쳐 같은 질문으로 다시 재면 시험 문제를 보고 공부한 셈이라 점수가 부풀려집니다.

| 단계 | 내용 |
|---|---|
| 1 | **사전 v2**: 문장 정의에 더해 **컬럼 매핑**을 명시한다(예: "결제 완료 = `paid_at`이 NULL이 아님, `status`와 무관"). 계산 SQL 자체는 여전히 주지 않는다 |
| 2 | **새로 만든 보류 질문 10개**로 v1과 v2를 비교한다(기존 20개는 v1 결과를 이미 보았으므로 평가에 쓰지 않음) |
| 3 | v2 결과는 "탐색적 후속 실험"으로 따로 표시하고 v1 판정과 섞지 않는다 |
| 4 (선택) | 사전 전체를 주는 방식 대신 **질문과 관련된 지표만 골라 주는 검색(RAG)** 방식이 Q19 같은 연결 실패를 줄이는지 본다 |
| 5 (선택) | `gemma-4-31b-it`(비추론형)를 대조군으로 추가해 추론형과 비추론형을 비교한다 |

> 📘 **개념 학습 — 시험 문제를 보고 고친 사전으로 같은 문제를 풀면 안 되는 이유**
> 결과에서 얻은 통찰로 시스템을 고치는 것은 좋은 엔지니어링입니다. 하지만 고친 시스템을 **같은 문제로** 평가하면 점수가 개선이 아니라 암기를 반영합니다. 그래서 개선 후에는 처음 보는 질문(보류 질문)으로 평가합니다. 머신러닝의 학습/검증 데이터 분리와 같은 원리입니다.
