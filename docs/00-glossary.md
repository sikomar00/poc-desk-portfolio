# 용어집

## 요약
문서에 나오는 용어를 "한 줄 정의 → 예시 → 이 프로젝트에서의 쓰임" 순서로 정리합니다. 새 개념이 나오면 이 표에 추가합니다.

## A. 기획 개념

| 용어 | 한 줄 정의 | 예시 | 이 프로젝트에서 |
|---|---|---|---|
| 문제 정의 | 해결책이 아니라 "무엇이 왜 곤란한가"를 말로 고정하는 일 | "앱이 없다"(X) / "매출 숫자가 사람마다 달라 보고서를 못 믿는다"(O) | [01](01-problem-definition.md) |
| 이해관계자 | 문제의 영향을 받거나 결과를 쓰는 사람들 | 현업, 분석가, PoC 담당자, 고객 IT | 01 |
| 가설 | 검증 전 "아마 이럴 것"이라는 추측. 반드시 확인 방법이 붙어야 함 | "정의서를 먼저 확정하면 재작업이 줄 것이다" | 01, 03 |
| 성공 지표 | 해결됐는지 숫자로 판단하는 기준 | 같은 질문 10번에 같은 숫자 10번 | 03 |
| 비목표(Non-goal) | 이번에 일부러 하지 않는 것. 범위가 번지는 걸 막음 | "자체 LLM 학습은 하지 않는다" | 03 |
| PRD | 제품 요구서. 무엇을/왜/어디까지/언제 성공인지 적은 문서 | 목표·기능·수용 기준 | [03](03-prd.md) |
| 수용 기준 | "이게 되면 이 기능은 완성"이라는 확인 가능한 조건 | "합계 차이 0원이면 통과" | 03 |
| 사용자 여정 | 사용자가 목표를 이루기까지의 단계와 감정 흐름 | 질문 → 대기 → 숫자 확인 → 의심 | [04](04-journey-and-flow.md) |
| 크리티컬 여정 | 끊기면 제품 가치가 사라지는 핵심 경로 하나 | 요구 입력 → 검증된 숫자 | 04 |
| IA(정보 구조) | 어떤 정보를 어떤 묶음·계층으로 둘지 | 메뉴: 접수 / KPI 사전 / 검증 / 리포트 | 04 |
| 화면 흐름 | 화면 간 이동과 분기를 그린 지도 | 접수 화면 → 정의서 → 결과 | 04 |

## B. 데이터·AI 개념

| 용어 | 한 줄 정의 | 예시 | 이 프로젝트에서 |
|---|---|---|---|
| BI | 데이터를 모아 분석·시각화해 의사결정을 돕는 일 | 대시보드, 월 매출 리포트 | 전체 |
| KPI | 핵심 성과 지표 | 월 매출, 재구매율 | 01 |
| KPI 사전(지표 정의서) | KPI마다 계산식·기준·제외 조건을 한 곳에 적은 표 | "매출 = 결제완료 − 취소, 부가세 제외, 결제일 기준" | 01, 03 |
| SQL | 데이터베이스에 묻는 언어 | `SELECT SUM(amount) FROM orders` | 03 |
| Text-to-SQL | 자연어 질문을 LLM이 SQL로 바꾸는 방식 | "이번 달 매출" → SQL | 03 |
| LLM | 대규모 언어 모델(GPT, Claude 등) | — | 03 |
| 환각(Hallucination) | LLM이 그럴듯하지만 틀린 답을 지어내는 현상 | 없는 컬럼명으로 SQL 작성 | 01 |
| 시스템 프롬프트 | LLM에게 미리 주는 역할·규칙 지침 | "KPI 사전에 없는 지표는 되묻는다" | 03 |
| RAG | 질문과 관련된 문서를 먼저 찾아 LLM에 붙여 답하게 하는 방식 | KPI 사전을 찾아 붙여 SQL 생성 | 03 |
| 검증(대사, Reconciliation) | 두 출처의 숫자를 맞춰 보는 일 | 리포트 합계 vs 원장 합계 | 03, 04 |

## C. PoC·개발 개념

| 용어 | 한 줄 정의 | 예시 |
|---|---|---|
| PoC | 개념 검증. "이 기술이 이 문제에 실제로 되는가"를 작게 확인 | 샘플 데이터 100건으로 정확도 측정 |
| 프로토타입 | 작동하는 시제품. PoC의 도구 | 로컬에서 도는 웹앱 |
| MVP | 가치를 확인할 수 있는 최소 제품 | 핵심 여정 하나만 되는 앱 |
| 재현 | 같은 입력으로 같은 오류를 다시 일으키는 일 | 버그 수정의 출발점 |

## D. 실험·검증 개념 (06, 07 문서에서 사용)

| 용어 | 한 줄 정의 | 예시 | 이 프로젝트에서 |
|---|---|---|---|
| 골드 답(정답 라벨) | 채점의 기준이 되는 사람이 확정한 정답 | 1월 매출 = 23,304,000원 | 06 |
| 정확도 | 결과가 정답과 같은 비율 | 100번 중 70번 정답 → 70% | 06 |
| 일치율 | 같은 질문을 여러 번 했을 때 같은 결과가 나오는 비율 | 5번 중 4번 같은 값 → 80% | 06 |
| 독립 변수 / 종속 변수 | 내가 바꾸는 것 / 그 결과로 측정하는 것 | 사전 유무 / 정확도 | 06 |
| 통제 변수 | 공정한 비교를 위해 고정하는 것 | 모델, 온도, 프롬프트 | 06 |
| 사전 등록 | 실험 전에 가설과 판정 기준을 고정해 두는 것 | "정확도 15%p↑이면 지지" | 06 |
| 신뢰구간 | 표본 비율이 진짜 값일 수 있는 범위 | 70% (60~78%) | 06 |
| 온도(temperature) | LLM 답변의 무작위성 정도. 0이면 거의 항상 같은 답 | 0.7 | 06 |
| 민감도 분석 | 정의 하나를 바꿀 때 결과가 얼마나 변하는지 재는 것 | W1~W7 비교표 | 05 |
| 대사 | 서로 다른 출처의 숫자를 맞춰 보는 일 | SQL 결과 vs 원장 | 05 |
| 허용 오차 | 같은 값으로 봐 주는 차이의 한계 | ±0.1% | 07 |
| 거짓 경보 | 맞는 값을 틀렸다고 경고하는 것 | 정답 36회 중 경보 0 | 07 |
| 놓침(미검출) | 틀린 값을 통과시키는 것 | 0.02% 오답 통과 | 07 |
| 검출률 | 틀린 값 중 걸러낸 비율 | 14개 중 14개 | 07 |
| 경보 정밀도 | 경보가 울린 것 중 진짜 오답인 비율. 기준선(전체 오답 비율)과 함께 봐야 함 | 경보 83개 중 52개 | 07 |
| 상관된 오류 | 서로 다른 모델이 같은 이유로 같은 틀린 값을 내는 것 | 둘 다 2.16% | 07 |
| 보류 질문(홀드아웃) | 개선 작업에 쓰지 않고 평가에만 쓰려고 따로 빼 둔 질문 | 사전 v2 평가용 10개 | 08 |
| 회귀 | 고치면서 다른 곳이 나빠지는 것 | 환불률 문구를 고쳤더니 취소율이 나빠짐 | 08 |
| 동결(해시) | 실험 전에 파일 내용을 고정하고 지문(해시)을 남겨 사후 변경을 막는 것 | 질문·사전 파일의 SHA-256 | 08 |
| 번짐(spillover) | 한 항목의 규칙을 강조했더니 다른 항목에도 잘못 적용되는 것 | 환불률 문구를 고쳤더니 취소율에도 `paid_at`이 끼어듦 | 09 |
| 천장 효과 | 비율 지표가 100%를 넘을 수 없어 기준이 달성 불가능해지는 것 | 기준선 56%에서 배수 최댓값 1.79 | 09 |
| 시맨틱 레이어 | 사람이 검토한 지표 정의·계산식을 한 곳에 두고 그것만 실행하게 하는 구조 | 검증된 환불률 SQL | 07 |
