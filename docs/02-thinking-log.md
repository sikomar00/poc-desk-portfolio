# 사고 흐름 기록

## 요약
면접에서 "왜 그렇게 했나요?"에 답하기 위한 기록입니다. 결정마다 **맥락 → 선택지 → 결정 → 이유 → 되돌릴 조건**을 남깁니다. 새 결정은 아래에 D-번호로 추가합니다.

## 기록 양식

```
### D-000 결정 제목
- 날짜:
- 맥락: 무엇을 정해야 했나
- 선택지: A / B / C
- 결정: 
- 이유: 
- 버린 것과 비용: 
- 되돌릴 조건: 이런 증거가 나오면 다시 생각한다
```

### D-001 두 공고를 하나의 포트폴리오로 묶는다
- 날짜: 2026-10-19
- 맥락: AI-BI 엔지니어와 신기술 R&D·PoC 엔지니어에 동시에 지원한다. 포트폴리오를 둘로 나누면 시간이 절반이다.
- 선택지: A) 공고별 별도 프로젝트 / B) 공통 문제 하나 + 공고별 적용 사례
- 결정: B
- 이유: 두 공고의 공통 구조가 "모호한 요구 → 과제 정의 → 구현 → 검증 → 문서화"이다. 이 구조 자체가 반복되는 문제이므로 프레임워크 하나로 두 역할을 모두 보여 줄 수 있다.
- 버린 것과 비용: 각 공고에 100% 특화된 깊이. 우대사항(Tableau, ETL 등)은 다루지 못함.
- 되돌릴 조건: 한쪽 공고의 마감·우선순위가 뚜렷이 앞서면 그쪽 시나리오를 더 깊게 한다.

- 이유: 무료 체험으로 시작할 수 있고(`[가정]` 개발 직전에 현재 조건 확인), 여러 모델을 갈아 끼워 비교하기 쉽다.
- 버린 것과 비용: 호출 한도와 모델별 SQL 품질 편차. 실험 결과에 사용한 모델명을 반드시 기록한다.
- 되돌릴 조건: 호출 한도·품질이 실험을 막으면 다른 API로 교체(설정만 변경).

### D-011 원장은 SQL이 아니라 파이썬으로 따로 계산해 정답표로 쓴다
- 날짜: 2026-10-19
- 맥락: SQL 결과가 맞는지 확인할 기준(정답)이 필요하다.
- 선택지: A) 같은 SQL을 정답으로 사용 / B) 생성 스크립트에서 파이썬으로 독립 계산
- 결정: B (`ledger` 테이블)
- 이유: SQL로 SQL을 검증하면 같은 실수를 같이 한다. 방법이 독립적이어야 대사의 의미가 있다.
- 버린 것과 비용: 정답이 '내 정의 v1에 대한 정답'일 뿐 현실의 진리는 아니다 (05 문서 5절에 한계로 명시).
- 되돌릴 조건: 실제 회계 확정치를 구할 수 있으면 그것을 정답으로 교체.

### D-012 환불 귀속월은 '원 결제월'로 정하고 충돌 ⑤로 추가한다
- 날짜: 2026-10-19
- 맥락: 환불이 다른 달에 일어나면 매출을 환불월에서 뺄지 결제월에서 뺄지 갈린다. 사용자가 요청한 4종 외에 데이터 생성 중 발견.
- 결정: 원 결제월에서 차감(정의 v1), 환불월 귀속은 오답 변형(V4)으로 보존.
- 이유: 월 매출이 사후에 소급 변동하지 않는 쪽이 보고서 안정성에 유리하다 `[가정]`.
- 되돌릴 조건: 고객사가 환불월 귀속을 쓴다면 정의 v2로 분리 (이것이 KPI 사전 버전 관리가 필요한 이유).

### D-013 실제 거래내역은 로컬 전용 '사례 B'로 추가한다 (합성 데이터는 공개 사례 A로 유지)
- 날짜: 2026-10-19
- 맥락: 합성 데이터만으로는 현실의 지저분함이 없고, 정답표(`ledger`)도 내 규칙으로 만든 값이라는 한계가 있다. 사용자가 뱅크샐러드 1년치 거래내역을 쓰겠다고 했다.
- 선택지: A) 합성만 / B) 실데이터만 / C) 합성(공개) + 실데이터(로컬 전용)
- 결정: C
- 이유: 개인정보를 공개하지 않으면서 '합성에서만 되는 게 아니다'를 보일 수 있다. 같은 프레임을 두 데이터에 적용한 비교가 회고 소재가 된다.
- 지킬 규칙: (1) 실데이터는 `data/private/`에만 두고 Git 제외 (2) LLM(외부 API)에는 테이블 구조와 KPI 사전만 보내고 거래 행은 보내지 않음 (3) 문서에는 집계·비식별 결과만 기록
- 버린 것과 비용: 실데이터 결과는 공개 재현이 불가능하다. 재현 가능한 쪽은 합성 사례 A가 담당.
- 되돌릴 조건: 비식별이 어렵다고 판단되면 사례 B는 결과 요약만 남기고 데이터 처리는 포기.


### D-014 '월 지출'에 저축·투자 이체를 포함한다
- 날짜: 2026-10-19
- 맥락: 사례 B에서 대분류 저축(48건)·투자(20건)는 타입이 전부 `이체`라서, 이체를 통째로 제외하면 빠진다. 포함 여부는 정의(무엇을 세나)의 문제이고 데이터가 답해 주지 않는다.
- 선택지: A) 제외(소비만 지출) / B) 포함(통장에서 나간 돈 전부)
- 결정: B (사용자 결정)
- 이유: 사용자는 '내 돈이 어디로 나갔나'를 기준으로 지출을 보고 싶어 한다. 정의는 목적에 따라 달라지며, 이 선택 자체가 KPI 사전에 기록돼야 하는 이유다.
- 주의한 점: 저축 48건은 전부 양수라 기록 방향이 모호하다. 절댓값으로 계산하되 통장 잔액 변동으로 검증하기 전까지는 `[가정]`이다. 투자는 순투입(음수=투입, 양수=회수)으로 계산.
- 버린 것과 비용: '소비 지출'과 '자금 이동'을 구분하는 보조 지표. 필요하면 정의 v2에서 `소비지출`과 `저축·투자`를 분리한다.
- 되돌릴 조건: 잔액 검증에서 저축 부호 가정이 틀리면 계산식을 고친다. 포함하면 월 비교가 왜곡되면 분리 지표로 바꾼다.


### D-015 앱 월 합계 대조로 '소비지출' 정의를 검증하고, 분리 가능성을 연다
- 날짜: 2026-10-19
- 맥락: 사례 B의 정답이 필요했다. 정답 후보 중 앱 화면 월 합계는 외부 출처다.
- 결과: 앱 합계는 W1(지출 타입 합계, 양수 차감, 이체 제외)과 11개월 모두 원 단위로 일치. 내 v1(저축·투자 포함)은 −48%~+120% 차이.
- 해석: 데이터 적재와 `소비지출` 계산은 검증됨. v1과의 차이는 오류가 아니라 정의 차이(D-014).
- 아직 안 한 것: 저축 부호 처리 검증(통장 잔액 변동 필요). 지표 분리(`소비지출`/`총유출`)는 사용자 확정 대기(Q11).
- 되돌릴 조건: 앱 정의가 바뀌거나 다른 기간에서 불일치가 나오면 재대조.


### D-016 '월 지출'을 `소비지출`과 `총유출` 두 지표로 나눈다 (Q11)
- 날짜: 2026-10-19
- 맥락: 앱의 '지출'은 `소비지출`(W1)과 11개월 모두 일치했지만, 사용자가 보고 싶은 '통장에서 나간 돈'은 저축·투자를 포함해 숫자가 −48%~+120% 다르다(D-014, D-015).
- 선택지: A) v1 하나에 이름 붙여 유지 / B) 두 지표로 분리
- 결정: B (사용자 결정)
- 이유: 한 이름에 두 정의가 섞이면 같은 질문에 두 숫자가 나오는 문제가 우리 프로젝트 안에서 재발한다. 각각 이름과 정의를 가지면 앱과의 차이도 '오류'가 아니라 '다른 지표'로 설명된다.
- 정의: `소비지출` = 타입 `지출` 합계(양수는 환불 차감, 이체 제외). `총유출` = `소비지출` + 저축 절댓값 + 투자 순투입.
- 검증 상태: `소비지출` 앱 합계와 11/11 일치. `총유출`의 저축 부호 처리는 `[가정]`(통장 잔액 변동으로 검증 필요).
- 되돌릴 조건: 잔액 검증에서 저축 처리가 틀리면 `총유출` 계산식만 수정한다(`소비지출`은 영향 없음).


### D-017 실험은 판정 기준을 먼저 고정하고, 사전에는 SQL을 넣지 않는다
- 날짜: 2026-10-19
- 맥락: H1을 검증하려면 어떤 결과가 나오면 '지지'인지, 사전에 무엇을 줄지 정해야 한다.
- 선택지: (기준) 결과를 본 뒤 판단 / 실행 전 고정. (사전 내용) 정의+SQL / 자연어 정의만
- 결정: 판정 기준(정확도 +15%p, 일치율 ≥90% 등)을 실행 전에 06 문서에 고정하고, KPI 사전에는 자연어 정의만 넣는다. LLM에는 거래 행을 보내지 않는다.

- 결정: B. 같은 `--run-id`로 재실행하면 `llm_error` 호출만 다시 시도하고, 평가기는 같은 호출의 마지막 기록만 쓰며 남은 장애 호출은 제외하고 알린다.
- 이유: 측정하려는 것은 모델과 사전의 품질이지 네트워크 상태가 아니다. v1 실험에서는 장애 호출이 0건이라 v1 결과에는 영향이 없다.
- 개정 절차: 실행 결과(스모크 4회의 정답 여부 포함)를 보기 전에 규칙을 바꾸고, 바뀐 파일의 해시를 08 문서에 갱신했다. 이것이 '동결 후 변경' 규칙의 예외 절차를 따른 사례다(사유를 먼저 기록, 결과를 보기 전에).
- 한계: 장애로 제외되는 호출이 특정 질문에 몰리면(예: 응답이 오래 걸리는 어려운 질문) 선택 편향이 생길 수 있다. 제외 개수와 질문을 보고한다.
- 되돌릴 조건: 장애가 전체의 10% 이상이면 결과를 제한적으로만 해석한다.


### D-028 사전 v2 결과는 사전 지정 규칙대로 기록하고, 기준의 결함은 인정하되 판정은 바꾸지 않는다
- 날짜: 2026-10-19
- 결과: Q-A 판정은 "개선되었으나 대조 질문에서 회귀"(표적 +66%p, 대조 −6%p). Q-B는 주 평가 B1에서 방법 1·3′ 모두 "불명".
- 결정: (1) 판정을 규칙대로 기록한다. 회귀(−6%p)는 임계값(−5%p)을 1%p 넘은 아슬아슬한 판정이고 호출 3개 차이라는 불확실성을 함께 적는다. (2) 검증 방법의 '기준선의 1.5배' 기준은 기준선이 56%일 때 최댓값이 1.79배라 정밀도 84% 이상이어야 통과하는 구조적 결함이 있음을 인정하지만, 이번 판정은 바꾸지 않는다. (3) 참고로 B2에서 방법 1이 '재현됨'이었어도 B2는 사전에 참고 조건으로 정했으므로 성공의 근거로 쓰지 않는다.
- 이유: 결과를 본 뒤 기준이나 주 평가 조건을 바꾸면 사전 지정의 의미가 없어진다(D-017, D-023, D-026의 연장).
- 얻은 것: 번짐(spillover)이라는 실질적 위험, 환불률 진단이 맞았다는 간접 증거, 배수 기준의 결함.
- 다음 기준: 새 실험에서는 기준선과 무관한 지표(검출률 − 거짓 경보율)를 쓰고, 임계값은 이번 결과를 보지 않은 새 데이터로 평가한다.
- 한계: 번짐 가설은 사후 가설이며 오답 값 검증으로는 일부 호출만 설명했다.
- 후속 선택지: A) 관련 지표만 제공(v3), B) 시맨틱 레이어, C) 마무리하고 포트폴리오 정리. 사용자 선택 대기.


### D-029 화면 앱은 설치가 필요 없는 로컬 웹앱으로 만든다
- 날짜: 2026-10-19
- 맥락: 포트폴리오의 가장 큰 약점이 "작동하는 화면이 없다"였다(공고의 '작동하는 결과물').
- 선택지: Streamlit / Flask / Electron / 표준 라이브러리 서버 + 순수 HTML·JS
- 결정: 표준 라이브러리 서버 + 순수 HTML·CSS·JS
- 이유: 채용 담당자가 `python app/server.py` 한 줄로 실행할 수 있고, 외부 패키지가 없어 의존성 위험도 없다.
- 버린 것과 비용: Streamlit은 코드가 훨씬 짧지만 설치가 필요하다. 화면 코드를 직접 써야 해 길어지고 유지 비용이 든다.
- 되돌릴 조건: 화면을 크게 확장해야 하면 프레임워크로 옮긴다.

### D-030 앱은 두 실행 방식을 제공하고 '검증됨'의 조건을 엄격히 한다
- 날짜: 2026-10-19
- 결정: (1) 검증된 계산식 모드(사람이 검토한 SQL 실행)와 AI 모드(LLM이 SQL 생성, 기준값·원장과 대조)를 둔다. (2) 사전에 없는 지표는 필수 4항목을 채우기 전에는 실행을 거부한다. (3) 정답 출처가 없는 지표는 어떤 방식이든 '검증 불가'로 표시한다.
- 이유: 실험 결과(07, 09)를 제품 규칙으로 옮긴 것이다. 오답이 모델의 체계적 습관이었고, 정답 출처가 없는 숫자는 어떤 방법으로도 '검증됨'을 붙일 수 없었다.
- 한계: 계산식 모드는 시맨틱 레이어 가설의 시제품이며 실험으로 평가하지 않았다. AI 모드는 가짜 LLM으로만 확인했다(실제 모델 호출 미검증).
- 되돌릴 조건: 계산식 모드를 평가해서 장점이 확인되면 기본 방식으로 격상, 아니면 AI 모드만 남기는 것을 재검토.


### D-031 거절하는 요청도 본문을 먼저 읽는다 (간헐적 테스트 실패의 원인은 서버 버그)
- 날짜: 2026-10-19
- 발견: 앱 테스트를 반복 실행하다 약 40% 확률로 `ConnectionAbortedError`가 나는 것을 봤다. 처음에는 한 번 통과한 테스트라 우연으로 넘길 뻔했다.
- 원인: 서버가 POST를 거절(403·415·413)할 때 요청 본문을 읽지 않고 응답해, 클라이언트가 본문을 보내는 도중 연결이 끊김. 브라우저에서도 거절 메시지를 못 받을 수 있는 실제 버그다.
- 결정: 응답 전에 본문을 먼저 읽는다. 너무 큰 본문은 2MB까지만 읽고 버리며 그 이상이면 연결을 닫는다. 고치기 전에는 실패하고 고친 뒤에는 통과하는 회귀 테스트를 추가한다(40회 연속 거절 요청).
- 확인: 테스트 21개를 25회 반복해 전부 통과(고치기 전에는 5회 중 2회 실패). 고치기 전 코드로 되돌려도 회귀 테스트가 실패함을 확인.
- 교훈: 간헐적 실패는 우연이 아니라 아직 설명하지 못한 원인이다. 한 번 통과한 테스트를 반복해서 돌려 본다.
- 함께 정정: 동결 해시 표 3개가 CRLF 상태의 해시였던 것을 저장소(LF) 기준으로 고쳤다(내용 동일, 줄바꿈만 다름. docs/08 참조).


### D-032 코드 리뷰 지적을 모두 반영하되, 끝난 실험 코드는 '동작을 보존'하는 수정만 하고 전후 출력을 비교해 증명한다
- 날짜: 2026-10-20
- 맥락: 코드 리뷰(app, experiment, data)에서 28건이 나왔다. 그중 일부는 이미 실험을 끝낸 동결 파일(`run_experiment.py`, `evaluate_v2.py`)에 있다. D-017, D-026은 '실행 후 바꾸지 않는다'고 했다.
- 선택지: A) 동결 파일은 건드리지 않고 알려진 결함으로 남긴다 / B) 판정·채점 동작은 그대로 두고 안전·견고성만 고치며, 바꾸기 전에 모든 출력을 저장해 두었다가 바꾼 뒤 비교한다
- 결정: B. 판정 임계값, 채점, 허용 오차, 질문, 사전, 샘플 DB, 실행 기록은 그대로 둔다. 실험 시점의 코드는 커밋 `54a9360`에 그대로 있다.
- 증거: 수정 전에 저장한 기준 출력 13개(본 실험 요약 2개, 보류 질문 평가, 대사, 분석 3개, 질문·골드 생성, 모의 실행 기록 3개와 요약·평가 포함)가 수정 후 **한 글자도 다르지 않았다**. 실험 직후 커밋한 출력 파일 4개도 그대로 재현되었다.
- 이 과정에서 새로 찾은 것: (1) 소급 시험 스크립트(`verify_without_gold.py`)가 holdout 기록 때문에 **지금 실행하면 오류로 죽고 있었다**. 커밋된 출력의 숫자는 맞았지만 '재현 가능'하지 않았다. (2) 생성 스크립트를 Windows에서 다시 돌리면 CRLF로 써서 동결 해시가 달라졌다. 둘 다 고쳤고 회귀 테스트를 남겼다.
- 고치지 않은 것(1건): `data/generate_sample_db.py`의 월말 경계 조건이 1월 28일 밤도 포함하는 문제. 고치면 샘플 DB의 모든 값이 바뀌어 끝난 실험 결과와 동결 해시가 무효가 되므로 코드에 주석으로 남기고 새 데이터 버전을 만들 때 고친다.
- 방법의 검증: 새 테스트가 정말 결함을 잡는지 확인하려고 수정한 동작을 일부러 되돌려 보았다(변이 시험). 되돌릴 때마다 해당 테스트가 실패했다.
- 되돌릴 조건: 수정이 끝난 실험 결과를 바꾸는 것으로 확인되면(전후 비교가 달라지면) 그 수정을 되돌린다.

### D-033 Supabase 이전은 3개 스키마로 나누고, 가계부는 API에 노출하지 않으며, 원본 행은 지우지 않는다
- 날짜: 2026-10-20
- 맥락: 로컬 SQLite 두 개(합성 주문, 실제 가계부)를 Supabase(Postgres)로 옮겨 "실제 데이터가 작동"하게 하고 싶다. 실제 가계부는 클라우드로 나가면 노출 위험이 생기고, 앱에는 LLM이 만든 SQL이 실행되는 경로가 있다.
- 선택지: A) 한 스키마에 `dataset` 컬럼으로 섞기 / B) 프로젝트 2개 / C) 한 프로젝트 안에서 스키마 3개 + 역할별 권한
- 결정: C. `demo`(공개 읽기), `personal`(API 비노출, 서버 직접 접속), `app`(정의·원장·기록, 모델은 직접 조회 불가). 원본 행은 지우지 않고 중복 의심은 `dup_group`으로 표시한다. 합성 데이터는 값을 바꾸지 않는다(D-032).
- 이유: 한 번의 권한 실수가 실제 데이터 노출로 이어지지 않게 하고, 끝난 실험의 동결 해시를 지키며, 중복 처리 같은 정의 선택을 데이터가 아니라 지표 정의에 둔다.
- 방법: `grill-with-docs` 스킬로 13개 질문을 3라운드 인터뷰했다. 질문마다 추천안을 붙였고 모두 승인되었다.
- 산출물: [13 문서](13-supabase-db-plan.md)(ERD 포함), [ADR 0001~0003](adr/), 루트 `GLOSSARY.md`.
- 하지 않은 것: 실제 이전, Supabase 프로젝트 생성, 앱 코드 전환.
- 되돌릴 조건: 가계부를 공개 데모와 완전히 분리해야 하면 프로젝트를 둘로 나눈다(ADR 0001).

### D-034 가계부 본인 확인은 서버 토큰으로, 앱은 SQLite를 기본값으로 둔 채 Postgres 모드를 추가한다
- 날짜: 2026-10-20
- 맥락: 가계부는 서버만 DB에 접속한다(ADR 0002). 그렇다면 Supabase Auth가 필요한지, 이전 후 기존 테스트 63개는 어떻게 지킬지 정해야 했다.
- 선택지: A) Supabase Auth 로그인 / B) 서버 환경변수 토큰 / C) 인증 없음(로컬 전용)
- 결정: B. 앱 코드는 접근 계층(`app/db.py`)으로 모으고 SQLite를 기본값, Postgres를 환경변수 선택으로 둔다.
- 이유: 사용자가 1명이고 브라우저가 DB에 직접 붙지 않아 로그인 서비스가 줄 이득이 없다. SQLite 기본값을 남겨야 이전 전후로 테스트와 대사를 같은 조건에서 비교할 수 있다.
- 한계: 서버를 외부에 배포하면 이 결정은 유효하지 않다. 그때 다시 정한다.
- 산출물: [14 문서](14-supabase-spec-and-tickets.md)(DDL 초안, 권한, 판정 기준, 티켓 T1~T8). DDL은 아직 Postgres에서 실행해 보지 않았다.
- 되돌릴 조건: 배포 계획이 생기거나 사용자가 둘 이상이 되면 A로 바꾼다.

### D-035 로그인은 Supabase Auth(본인 1계정)로 하고, D-034의 서버 토큰 방식을 대체한다
- 날짜: 2026-10-20
- 맥락: 로그인 기능을 넣고 싶다는 요청. D-034는 "서버 환경변수 토큰, Supabase Auth 미사용"이었다.
- 선택지: A) 서버 토큰 유지 / B) Supabase Auth / C) 자체 users 테이블
- 결정: B. 가입은 닫고 본인 계정 1개, 비로그인은 합성 데이터만(공개 데모). `app.profiles`를 두고 `owner_id`가 이를 가리키며 `query_runs`에 `user_id`를 추가한다. 로그인 성공·실패 기록 테이블과 비밀번호 재설정 화면은 만들지 않는다.
- 이유: 사용자 구분과 실행 기록이 필요해졌고, 비밀번호 저장·세션은 직접 만들수록 위험하다. 가계부 조회는 계속 서버 직접 접속이라 ADR 0002는 유지된다.
- 방법: `grill-with-docs`로 6개 질문을 2라운드 인터뷰, 모두 추천안 승인.
- 산출물: [erd.md](../erd.md)(ERD·로그인 흐름), [ADR 0004](adr/0004-supabase-auth-replaces-owner-token.md).
- 하지 않은 것: Supabase 프로젝트 생성, 코드 구현, 14 문서 DDL의 실행.
- 되돌릴 조건: 사용자가 1명이고 사용자 구분이 필요 없다고 판단되면 D-034로 돌아간다.

### D-036 Supabase 구축은 새 프로젝트(서울)에 CLI로, 마이그레이션 파일로만 바꾼다
- 날짜: 2026-10-20
- 맥락: 이 세션에는 Supabase 커넥터가 없었다(설치·레지스트리 모두 없음, GitHub 커넥터도 인증 오류). 같은 조직에 어제 만든 프로젝트(뭄바이)가 이미 있었다.
- 선택지: A) 커넥터 추가 대기 / B) Supabase CLI(npx) / C) 대시보드에서 수동 생성
- 결정: B. 기존 프로젝트는 건드리지 않고 `realdefinition`을 서울에 새로 만들었다. DB 변경은 `supabase/migrations/`의 파일로만 하고, 권한은 실제 로그인으로 검증한다.
- 이유: 로그인은 브라우저 승인 방식이라 비밀번호·토큰을 채팅에 붙일 필요가 없고, 마이그레이션 파일은 저장소에 남아 재현할 수 있다.
- 한계: 설정 변경(`config push`)은 한 번에 많은 값을 바꾸므로 반드시 차이를 먼저 보고, 의도하지 않은 값(MFA, 저장소 등)은 원격 값에 맞춰 둔 뒤 적용했다.
- 하지 않은 것: 데이터 적재, GitHub 저장소 연동(대시보드 승인 필요), 앱 코드 전환.
- 되돌릴 조건: 프로젝트를 지우고 같은 마이그레이션으로 다시 만들 수 있다.

### D-037 앱 연결은 접근 계층 한 곳과 공식 인증서 검증으로, 로그인 확인은 서버가 Supabase Auth에 직접 묻는다
- 날짜: 2026-10-20
- 맥락: 앱을 Supabase에 연결하려면 파이썬에 Postgres 접속 도구가 필요하다(표준 라이브러리에는 없다). 접속 서버의 인증서는 컴퓨터 기본 신뢰 목록에 없었다.
- 선택지: 도구 — A) pg8000을 앱 폴더에만 설치 / B) Supabase CLI를 매 질문마다 호출. 인증서 — C) 공식 루트 인증서로 검증 / D) 검증 끄기 / E) 지금 받은 인증서를 그대로 신뢰. 로그인 확인 — F) 서버가 토큰을 Auth에 확인 + 프로필 확인 / G) 토큰 서명을 앱이 직접 검증
- 결정: A, C, F. 사용자가 A와 C를 승인했다. 접속은 `app/db.py` 한 곳을 거치고 SQLite를 기본값으로 남긴다(D-034).
- 이유: B는 질문당 수 초가 걸리고, D·E는 DB 비밀번호가 오가는 연결을 가로채기에 약하다. G는 키 교체(서명 키 회전)를 앱이 따라가야 해서 F가 단순하다.
- 한계: 서버가 토큰 검증마다 Auth를 호출한다(30초 캐시). 사용자 정의 지표와 가계부는 아직 DB로 가지 않았다.
- 산출물: `app/db.py`, [14 문서](14-supabase-spec-and-tickets.md) 앱 연결 기록, 마이그레이션 0004.
- 되돌릴 조건: 환경변수 `POC_DESK_BACKEND`를 지우면 즉시 SQLite로 돌아간다.

### D-038 앱의 첫 보강은 '정의 비교' 화면: 문제를 설명하지 않고 화면에서 보여 준다
- 날짜: 2026-10-20
- 맥락: 앱이 질문 → 숫자 하나 → 대사 정도만 해서 기능이 얇다는 지적이 있었다. 이 프로젝트의 핵심 주장("정의가 다르면 같은 질문에 다른 숫자가 나온다")이 앱 화면에서는 드러나지 않았다.
- 선택지: A) 정의 비교 화면 / B) 가계부 연결 / C) 월별 추이·분해 같은 일반 BI 화면 / D) 전체 계획부터
- 결정: A (사용자가 선택). B는 가명 처리 규칙을 먼저 정해야 하고 되돌리기 번거로워 다음 순서로 둔다.
- 방법: 새 계산식을 만들지 않고 이미 검증한 정의 6가지(V0~V5)를 그대로 쓴다. 정의마다 달라지는 네 가지 선택을 풀어 쓰고, 공식 정의가 원장과 일치하는지 함께 보여 준다. Supabase용은 날짜 함수만 자동 변환한다.
- 증거: 1~3월 매출이 정의에 따라 최대 19,706,900원(31.4%) 달라진다. SQLite와 Supabase의 18개 월별 값이 모두 같다. 테스트 48개 통과.
- 한계: '매출'에만 있다. 환불률 등은 정의 변형이 아직 없다. 가계부(소비지출 vs 총유출)에는 같은 방식이 가능하지만 아직 연결하지 않았다.
- 되돌릴 조건: 카드를 쓰지 않으면 화면에서 버튼을 누르지 않는 한 아무 일도 일어나지 않는다(기록·권한 변경 없음).

### D-039 앱을 Vercel에 공개 데모로 배포한다: 같은 코드, 공개 전용 규칙, 최소 권한 비밀만 올림
- 날짜: 2026-10-20
- 맥락: 포트폴리오에서 면접관이 설치 없이 눌러 볼 수 있어야 한다. Vercel 커넥터는 이 세션에 없어서 Vercel CLI(브라우저 로그인)로 진행했다. 앱은 내 PC 전용으로 만들어서(`127.0.0.1`만 허용, 파일 저장) 그대로는 인터넷에 올릴 수 없었다.
- 선택지: A) 앱 전체를 공개 데모로 / B) 점검 화면(정적)만 / C) 보류
- 결정: A(사용자 선택). 같은 서버 코드를 `POC_DESK_PUBLIC=1`일 때만 공개 규칙으로 돌린다: 같은 출처 요청만 허용, 비로그인 실행은 DB에 기록하지 않음, 정의 저장 끔, 속도 제한, HTTPS 헤더, AI 모드는 키를 올리지 않아 꺼짐. Vercel에는 **읽기 전용 계산 역할과 서비스 역할의 비밀번호만** 올리고 가계부 역할·관리자 비밀번호는 올리지 않는다. 배포 보호를 끄는 것(공개 전환)은 사용자가 명시적으로 승인했다.
- 이유: 면접관이 바로 눌러 볼 수 있는 주소가 포트폴리오에 가장 효과가 크다. 위험은 (1) 합성 데이터만 노출하고 (2) DB 역할을 최소 권한으로 두고 (3) 누구나 DB에 쓰지 못하게 막아 줄였다.
- 발견한 문제: 환경변수 기본값 미유지, 요청 경로 재작성, 연결 지연(12초 → 1.9초), 풀러에서 역할 검색 경로 미적용, 진단 코드 문법 오류. 전부 [16 문서](16-vercel-deployment.md)에 기록했다.
- 한계: 속도 제한은 인스턴스별 근사치라 완전한 방어가 아니다. 무료(Hobby) 플랜은 비상업 용도다.
- 자동 배포: GitHub의 Vercel 앱을 이 저장소 하나에만 설치해 연결했고, `main` 푸시가 사람의 배포 명령 없이 운영 배포로 이어짐을 커밋 상태(success)로 확인했다.
- 되돌릴 조건: `vercel project protection enable --sso`로 비공개로 되돌리거나 프로젝트를 지우면 된다. 내 PC 모드는 영향이 없다.
