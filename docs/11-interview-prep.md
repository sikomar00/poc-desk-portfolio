# 면접 준비 노트

## 요약
공고는 "본인이 구현한 내용과 선택의 이유, 어려웠던 점을 설명할 수 있는 분"을 원합니다. 이 프로젝트는 **AI 어시스턴트와 협업**해서 만들었으므로, 면접에서 가장 중요한 것은 **내 말로 설명할 수 있는가**입니다. 이 노트는 예상 질문마다 **한 줄 답, 근거 문서, 정직하게 덧붙일 한계**를 정리합니다. 답을 외우지 말고 근거 문서를 열어 읽은 뒤 자기 말로 바꿔 보세요.

## 1. 먼저 외울 숫자 7개

| **11/11** | 가계부 "소비지출" 계산이 앱의 월 합계와 11개월 모두 일치 | 05 7-9 |

## 2. 예상 질문과 답변 근거

**Q1. 이 프로젝트를 한 문장으로 설명해 주세요.**
같은 질문에 AI와 사람이 서로 다른 숫자를 내는 문제를, KPI 정의를 확정하는 방식으로 줄일 수 있는지 실험하고 검증한 프로젝트입니다. → [PORTFOLIO](../PORTFOLIO.md) 1절

**Q2. 왜 이 문제를 골랐나요?**
두 공고가 공통으로 요구하는 게 "모호한 요구를 정의하고, 만들고, 검증하고, 문서화하는 능력"이었고, 지표 정의 불일치는 BI의 핵심 문제이면서 LLM이 특히 위험하게 만드는 문제라서입니다. 후보 6개 중 SQL, 지표, AI, 검증이 모두 들어가는 것을 골랐습니다. → 결정 D-001, D-002 ([02](02-thinking-log.md))

**Q3. KPI 사전이 왜 필요한가요?**
"매출"에 부가세 포함 여부, 취소·환불 처리, 기준 날짜가 정해져 있지 않으면 같은 데이터에서 숫자가 최대 36% 달라졌습니다. 사전은 지표마다 계산식, 포함·제외, 기간 기준, 단위를 한 곳에 확정합니다. → [05](05-data-design.md) 4절

**Q4. 실험은 어떻게 설계했나요?**
사전 유무만 다른 두 조건(A: 테이블 구조만, B: 구조 + 사전)을 20개 질문 × 5회로 비교했습니다. 질문, 정답, 채점 규칙, 판정 기준을 실행 전에 고정했고, 정답은 SQL과 파이썬으로 따로 계산해 서로 맞는지 확인했습니다. → [06](06-experiment-design.md)

**Q5. 정확도가 +52~65%p 올랐는데 왜 "불명"인가요? 실패 아닌가요?**
성공 조건을 "정확도 +15%p 이상 **이고** 일관성 90% 이상"으로 미리 정했는데, 일관성이 71~74%였기 때문입니다. 정확도는 올랐지만 같은 질문을 5번 물었을 때 같은 숫자가 나오는 비율이 낮아서, "믿을 수 있다"고는 말할 수 없었습니다. 기준을 낮춰 성공으로 쓰지 않았습니다. 다만 90%는 직감으로 정한 값이라 현실적인지는 회고에서 다시 따졌습니다. → [07](07-experiment-results.md) 2절

**Q6. AI가 만든 SQL을 어떻게 믿나요?**
정답 출처가 있는 지표(매출)는 원장과 대사해서 정확히 일치하지 않으면 경고합니다. 허용 오차를 0.1%만 둬도 거의 맞는 오답 3개를 놓쳤기 때문에 허용 오차는 0으로 했습니다. 정답 출처가 없는 지표(환불률)는 검증기가 아니라 "사람이 볼 후보를 추리는" 신호만 가능했습니다(교차 모델 불일치, 정밀도 63%). → [07](07-experiment-results.md) 6~7절

**Q7. 가장 어려웠던 점이나 실수는?**
실험 입력에 정답표가 섞여 있는 것을 발견한 일입니다. 조건 A도 정답을 베낄 수 있었습니다. 모의 실행의 프롬프트를 직접 읽다가 알았고, 정답표를 숨기고 접근도 차단했습니다. 또 환불률 오답을 "사전 문구가 모호해서"라고 해석했다가 데이터로 확인하니 명시된 규칙을 모델이 따르지 않은 것이어서 문서를 정정했습니다. → [10](10-retrospective.md) 3절

**Q8. 실제 데이터는 어떻게 다뤘나요? 개인정보는요?**
가계부 1년치를 로컬 전용 폴더에 두고 Git에서 제외했습니다. LLM에는 테이블 구조와 사전만 보내고 거래 행은 보내지 않았으며, 공개 문서에는 건수와 비율만 적었습니다. → 결정 D-013, [05](05-data-design.md) 7절

**Q9. 왜 그 모델들을 골랐나요?**
처음 고른 모델은 계정에서 호출이 안 돼서(404), 22개를 실제로 호출해 4개만 쓸 수 있음을 확인했습니다. 그중 둘 다 추론형이라 크기만 다른 조합(약 120B와 20B)을 골랐습니다. 한 문제의 정답 여부로는 고르지 않았습니다. → D-021, [06](06-experiment-design.md) 12절

**Q10. 결과의 한계는?**
모델 2개, 온도 하나, 질문 30개, 합성 데이터라 일반화할 수 없습니다. 질문과 사전을 같은 사람이 썼고, 정답은 제가 정한 정의에 대한 정답입니다. → [PORTFOLIO](../PORTFOLIO.md) 6절

**Q11. 사전을 고친 뒤 어떻게 검증했나요?**
같은 질문으로 다시 재면 점수가 부풀려져서, 새 질문 10개를 만들어 이전 사전(v1)과 새 사전(v2)을 함께 평가했습니다. 표적은 +66%p 올랐지만 고치지 않은 지표가 −6%p 떨어져 "회귀"로 판정했습니다. 문구를 바꾸지 않은 취소율에서 정답이 줄었고, 번짐일 수 있다고 보지만 아직 가설입니다. → [09](09-experiment-v2-results.md)

**Q12. 이걸 실제 고객 환경에 적용하려면?**
(모르면 정직하게) 이 프로젝트는 고객 환경 설치와 ERP/CRM 연동을 다루지 않았습니다. 필요한 것은 실제 현업과 지표 정의를 합의하는 절차, 정답 출처(회계 확정치 등) 확보, 권한과 보안 확인입니다. 정의를 확정하는 양식과 대사 방식은 그대로 쓸 수 있다고 봅니다.

**Q13. 다시 한다면 무엇을 바꾸겠나요?**
질문별로 관련 지표 정의만 주는 방식을 시험하고(번짐 가설 확인), 검증된 지표 계산식을 직접 실행하는 시맨틱 레이어를 시도하겠습니다. 질문 작성자와 사전 작성자를 분리하고, 판정 기준은 오답 비율에 영향받지 않는 지표로 바꾸겠습니다. → [10](10-retrospective.md) 6절

**Q14. AI 도구를 썼다고 했는데, 어디까지 직접 하셨나요?**
(본인의 실제 역할에 맞게 고쳐서 답하세요.) 예시: 방향 선택, 정의 확정(저축·투자를 지출에 넣을지, 지표를 둘로 나눌지 등), 결과의 채택·기각 판단은 제가 했고, 코드와 문서 초안은 AI와 함께 작성한 뒤 모의 실행, 파이썬 재계산, 단위 테스트로 검증했습니다. 판단은 결정 기록에 남아 있습니다. → [02](02-thinking-log.md)

**Q15. 화면 앱은 어떻게 만들었고, 어디까지 확인했나요?**
설계한 크리티컬 여정(질문 → 정의 확인 → 계산 → 정답 대조 → 리포트)을 Python 표준 라이브러리만으로 만든 로컬 웹앱입니다. 정의가 없는 지표는 실행을 거부하고, 정답 출처가 없는 숫자에는 "검증됨"을 붙이지 않습니다. 테스트 48개와 브라우저 조작으로 확인했습니다. AI 모드는 처음엔 가짜 LLM으로만 확인했다가, 나중에 실제 모델(gpt-oss-20b)로 로컬 5회·공개 주소 1회 호출해 모두 대사를 통과했습니다. **표본이 작아 정확도 주장은 하지 않고**, 공개 데모에서는 방문자에게 AI 모드를 닫아 두었습니다(비용·남용 방지, 본인 로그인에만 열림). → [12](12-poc-desk-app.md)

**Q16. 코드 리뷰 결과는 어떻게 처리했나요? 이미 끝난 실험 코드를 고쳐도 되나요?**
리뷰로 29건이 나왔고 의심 항목을 직접 실행해 6건을 재현했습니다. 끝난 실험 코드는 판정 임계값, 채점, 질문, 사전을 그대로 두고 안전과 견고성만 고쳤습니다. 고치기 **전에** 모든 출력을 저장해 두었다가 고친 **뒤에** 비교해서, 13개 출력이 한 글자도 달라지지 않았음을 확인했습니다. 이 비교 덕분에 소급 시험 스크립트가 이미 지금 실행하면 죽고 있었다는 사실도 찾았습니다. 새 테스트는 수정한 동작을 일부러 되돌려 보는 변이 시험으로 검증했습니다. → [02 결정 기록 D-032](02-thinking-log.md)

**Q17. 앱에 "정의 비교" 화면을 넣은 이유는 뭔가요?**
이 프로젝트의 핵심 주장은 "정의가 다르면 같은 질문에 다른 숫자가 나온다"인데, 처음 만든 앱은 확정한 정의 하나만 계산해서 그 문제가 화면에 안 보였습니다. 그래서 실험에서 쓴 정의 6가지를 그대로 가져와 같은 1분기 매출을 나란히 보여 줍니다(62,831,000원~82,537,900원, 최대 31.4%). 새 계산식을 만들지 않고 이미 검증한 정의를 재사용했고, 공식 정의만 원장과 일치함을 같이 보여 줍니다. → [12](12-poc-desk-app.md), [D-038](02-thinking-log.md)

**Q18. Supabase로 왜 옮겼고, 보안은 어떻게 했나요?**
"실제 데이터가 작동하게"가 목표였고, 클라우드 DB 연동 경험을 만들기 위해서였습니다. 합성 데이터는 공개 읽기, 가계부는 API에 노출하지 않는 별도 스키마, 지표 정의·원장은 모델이 못 읽는 스키마로 나눴습니다. 모델이 만든 SQL은 읽기 전용·5초 제한 역할로만 실행하고 서버 인증서를 공식 인증서로 검증합니다. 비밀번호는 저장소에 두지 않았습니다. **다만 실제 가계부는 아직 올리지 않았고**, 합성 데이터와 본인 1계정 기준입니다. → [13](13-supabase-db-plan.md), [14](14-supabase-spec-and-tickets.md)

**Q19. QA는 어떻게 했나요? 찾은 문제가 있나요?**
자동 테스트(앱 48, 실험 32)와 별개로, 원격 DB의 권한과 로그인을 직접 확인하는 점검 화면을 만들고 점검표 59건을 스프레드시트에 기록했습니다. 가입을 닫을 때 이메일 로그인까지 꺼 둔 설정 실수, 알림 창이 안 보여 로그인이 반응 없어 보인 문제, 진단 경고의 오탐을 이 과정에서 찾았고, 오탐은 실행 계획으로 근거를 확인했습니다. 실패한 항목(재설정 링크 토큰 변형)은 원인을 모른 채 실패로 남겼습니다. → [15](15-supabase-qa-guide.md)

**Q20. 이 앱이 실제로 쓸모가 있나요? (솔직한 질문)**
도구로서는 얇습니다. 합성 데이터의 지표 5개이고 질문 해석은 키워드 사전입니다. 이 프로젝트의 증거는 앱이 아니라 문제 정의, 판정 기준을 미리 고정한 실험, 그리고 틀린 것을 기록한 과정에 있습니다. 앱은 그 주장을 눈으로 보여 주는 시연 도구이고, 다음 단계는 실제 가계부에 같은 정의 비교를 적용하는 것입니다. → [PORTFOLIO](../PORTFOLIO.md) 6절

## 3. 직접 설명 연습 (이게 안 되면 면접이 어렵습니다)

AI 도움으로 만든 결과물은 **내가 설명할 수 있어야** 내 것입니다. 자료를 보지 않고 각각 1분씩 말해 보세요.

- [ ] 정확도와 일치율의 차이를 예시로 설명할 수 있다 (항상 같은 오답이면?)
- [ ] 사전 등록(판정 기준 사전 고정)이 왜 필요한지 설명할 수 있다
- [ ] 보류 질문과 회귀 확인이 왜 필요한지 설명할 수 있다
- [ ] 대사가 무엇이고 허용 오차를 0으로 둔 이유를 설명할 수 있다
- [ ] `run_experiment.py`가 한 번 호출할 때 거치는 단계(프롬프트 → 호출 → SQL 추출 → 안전 검사 → 읽기 전용 실행 → 채점 → 기록)를 말할 수 있다
- [ ] 정답표가 유출된 것을 어떻게 발견했고 어떻게 고쳤는지 말할 수 있다
- [ ] 이 프로젝트가 **하지 못한 것**을 먼저 말할 수 있다

## 4. 면접 태도 팁

- **모르면 모른다고 말하고, 어떻게 알아낼지를 말하세요.** 이 프로젝트의 내용 자체가 "확인하지 못한 것을 사실처럼 쓰지 않는다"입니다.
- **결과가 "불명"인 것을 숨기지 마세요.** 기준을 지킨 점이 장점입니다.
- **한계를 먼저 말하면 신뢰가 올라갑니다.** 질문받기 전에 "이 실험은 이런 한계가 있습니다"로 시작해 보세요.
- 공고가 중시하는 **소통과 태도**: 질문에 막히면 되묻고, 피드백을 받아들이는 모습(이 프로젝트의 정정 기록들)을 근거로 말하세요.
