# Supabase QA 가이드

## 요약
Supabase에 만든 DB가 설계대로 동작하는지 **직접 눌러서 확인**할 수 있는 화면(`qa/index.html`)과, 그 화면으로 볼 수 없는 부분(가계부·정의·원장)을 제가 실제 역할로 로그인해서 확인한 결과를 정리했습니다. QA 화면은 공개(anon) 키만 쓰며, 앱(PoC Desk) 자체는 아직 SQLite를 씁니다(T8에서 전환).

## 1. 화면 열기
```powershell
cd C:\realDefinition
python qa/make_config.py
cd qa
python -m http.server 8770 --bind 127.0.0.1
```
브라우저에서 `http://127.0.0.1:8770/index.html`을 엽니다. `make_config.py`는 로그인된 Supabase CLI로 공개 키만 가져와 `qa/config.js`(git 제외)를 만듭니다. 끄려면 서버를 띄운 창에서 `Ctrl + C`.

## 2. 직접 해볼 것 (쉬운 순서)
| # | 해볼 것 | 정상이라면 |
|---|---|---|
| 1 | **“전체 점검 실행”** 클릭 | 12 / 12 통과 |
| 2 | “3. 데이터 둘러보기”에서 테이블을 바꿔 가며 “앞 20행 보기” | 주문·고객 등 가짜 데이터가 보인다 |
| 3 | 로그인 칸에 **틀린 비밀번호**를 넣고 로그인 | “로그인 실패”가 나온다(거절되어야 정상) |
| 4 | **본인 계정**으로 로그인 → “로그인 상태 점검” | 5개 항목 모두 통과, 로그인해도 가계부·app은 여전히 안 보인다 |
| 5 | 비밀번호를 잊었다면: 대시보드 Authentication > Users에서 본인 계정의 **Send password recovery** → 메일 링크를 열면 QA 화면의 “새 비밀번호 설정”이 나온다(**QA 서버가 켜져 있어야 한다**) | 새 비밀번호 저장 후 로그인 성공 |
| 6 | 로그아웃 후 새로고침 | 로그인 상태가 풀린다(비밀번호는 저장하지 않는다) |
| 7 | (선택) Supabase 대시보드 > Table Editor에서 `demo.orders`를 열어 화면 숫자와 비교 | 500행 |

로그인 점검(4번)은 **제가 대신할 수 없습니다.** 비밀번호를 채팅에 쓰지 않는 것이 원칙이라, 직접 해 보시고 결과만 알려 주세요.

## 3. 점검 항목 12개가 말해 주는 것
| # | 확인 | 의미 |
|---|---|---|
| 1~5 | `demo` 테이블 5개의 행 수 | 이전된 데이터가 로컬과 같은 개수 |
| 6 | 결제월별 주문 수·상품금액·총액 | 숫자가 로컬 SQLite와 한 글자도 다르지 않다 |
| 7~8 | 공개 키로 쓰기·지우기 시도 | 공개 데모가 오염되지 않는다 |
| 9~10 | `personal`·`app` 접근 | 가계부와 정답 원장은 인터넷에서 닿지 않는다 |
| 11 | 낯선 사람의 회원가입 | 가입이 닫혀 있다 |
| 12 | 틀린 비밀번호 로그인 | 로그인 기능이 살아 있고 잘못된 비밀번호는 거절된다 |

## 4. QA 화면으로 볼 수 없는 부분 — 제가 확인한 결과
가계부(`personal`)와 정의·원장·기록(`app`)은 일부러 API에 노출하지 않아서 브라우저로는 볼 수 없습니다. 임시 테스트 데이터(가짜 가계부 3건, 가짜 지표 정의 1건)를 넣고 **실제 역할로 로그인**해서 확인했고, 끝난 뒤 전부 지웠습니다(현재 `demo.orders` 500행, 프로필 1개, 나머지는 비어 있음).

| 확인 | 결과 |
|---|---|
| `poc_reader_personal`이 본인 ID 지정 없이 가계부 조회 | 0건 |
| 본인 ID를 지정한 접속으로 조회 | 3건, 합계 −6,000원, 중복 의심 표시 1건 |
| 가계부·카테고리·결제수단 조인 | 정상 |
| `app_service`가 지표 정의·원장·실행 기록 추가 | 성공 |
| 로그인하지 않은 공개 데모 실행(`user_id` 없음) 기록 | 성공 |
| 같은 지표·같은 버전 정의를 한 번 더 추가 | 거부(유일 키) |
| 형식이 틀린 월(`2026-1`) 원장 추가 | 거부(검사 규칙) |
| 존재하지 않는 사용자로 실행 기록 추가 | 거부(외래키) |
| 실행 기록 수정(UPDATE) | 거부(추가만 가능) |
| 읽기 전용 역할 로그인 시 설정 | 읽기 전용 on, 제한 시간 5초, `pg_sleep(10)`은 취소됨 |

## 5. QA가 찾아낸 문제와 처리
| 문제 | 원인 | 처리 |
|---|---|---|
| 가입을 닫았더니 **이메일 로그인까지 거절**(“Email logins are disabled”) | 가입을 닫는 설정 두 개 중 `auth.email.enable_signup`은 “이메일 방식 전체”를 끄는 스위치였다. 가입 닫기는 전역 `auth.enable_signup = false` 하나로 충분하다 | `auth.email.enable_signup`을 다시 켜서 반영. 가입은 여전히 거절(422), 틀린 비밀번호는 400으로 거절 |
| 로그인 카드가 **이상하게 보였다** — 로그아웃·상태 점검 버튼과 “새 비밀번호 저장” 줄이 로그인 전에도 항상 보이고, 입력 칸에 이름표가 없었다 | `hidden`으로 숨긴 줄에 `display:flex` 스타일이 덮어써서 숨겨지지 않았다(화면 점검 중 스크린샷으로 발견) | 카드를 새로 설계: 상태(로그아웃 / 로그인됨 / 비밀번호 재설정 중)마다 패널 하나만 보이고 카드 머리에 상태 표시, 이름표가 있는 입력 칸·비밀번호 보기 버튼·Enter 제출, 로그인 후 계정 표시와 세션 남은 시간 카운트다운, 결과 표는 점검을 시작할 때만 표시. 모바일(375px)·라이트/다크에서 확인 |
| 로그인 버튼을 눌러도 **아무 반응이 없어 보였다** | 결과를 `alert` 창으로만 알렸는데, 앱 안의 브라우저에서는 알림 창이 보이지 않거나 막힐 수 있다. 사용자가 비밀번호 오류인지 고장인지 구분할 수 없었다 | 화면 안에 상태 메시지를 표시(“로그인 중…”, 성공, 실패 이유), Enter 키로도 로그인. 틀린 비밀번호는 “이메일 또는 비밀번호가 맞지 않습니다”, 서버 설정 문제는 “비밀번호 문제가 아닙니다”로 구분해 알려 준다 |
| 비밀번호 재설정 링크가 `127.0.0.1:8765`로 이어져 **접속할 수 없었다** | Supabase의 사이트 주소가 실행 중인 서버도, 재설정 화면도 없는 8765(앱)로 되어 있었다 | 사이트 주소를 QA 서버(`http://127.0.0.1:8770`)로 바꾸고, QA 화면에 “새 비밀번호 설정” 화면을 추가. 임시 계정으로 링크 → 새 비밀번호 저장 → 로그인 → 로그인 점검 5/5까지 확인하고 임시 계정은 삭제 |
| 설정을 바꾼 직후에는 한동안 예전 응답이 나왔다 | 설정 반영에 수 초가 걸린다 | 8초 뒤 다시 확인해 정상 확인 |
| 적재·점검 중 SQL 한 줄이 연결 방식에 따라 여러 문장을 못 보냈다 | 풀러(db-url) 연결은 한 번에 한 문장만 받는다 | 점검 SQL을 문장 단위로 나눠 실행 |

> 📘 **개념 학습 — QA에서 “통과”보다 “실패”가 값진 이유**
> 12개 중 11개가 통과했을 때 실패 1개가 **본인도 로그인할 수 없는** 설정 실수를 잡아냈습니다. 가입 거절 점검만 있었다면 “닫혔다”로 통과했을 겁니다(로그인이 막혀서 가입도 막힌 것이므로). 그래서 “닫아야 할 것”과 “열려 있어야 할 것”을 **함께** 점검합니다.

**사용자가 직접 확인한 것 (2026-10-20):** 새로 만든 본인 계정으로 QA 화면에서 로그인에 성공했고 “로그인 상태 점검” 5개가 모두 통과했다. (이 과정에서 재설정 링크의 토큰이 변형되는 문제가 있어 계정을 새로 만들었다. 원인은 확인하지 못했고, 화면은 이제 변형된 토큰을 열자마자 알려 준다.)

## 6. 아직 확인하지 못한 것
- 앱 서버가 JWT를 검증하고 `app.profiles`를 확인한 뒤 가계부를 읽는 전체 경로(T8).
- 실제 가계부 데이터 적재(T5~T6)와 정의·원장 이전(T7).
- 무료 플랜의 일시정지·백업·용량 한도.
